# Производительность и пайплайн 3D-ассетов

Документ для тех, кто правит код рендера или добавляет новые модели. Коротко: игра должна держать 60 FPS на встроенной графике (эталон — Intel UHD 770, 1920×1080) и быстро грузиться с GitHub Pages.

---

## 1. Как измерять

- **F3** в игре (или `?perf` в адресе) — оверлей: FPS по реально отрисованным кадрам, CPU-время `update()` и `render()`, число врагов, частиц и пуль. Зелёный — норма, красный — кадр дольше 18 мс. Время GPU оверлей не показывает.
- Для глубокого разбора — вкладка **Performance** в Chrome DevTools.
- ⚠️ **Не замеряйте GPU через `ctx.getImageData()` каждый кадр.** После нескольких чтений подряд Chrome переводит канвас в программный (CPU) режим, и все цифры становятся неправдой. Если нужно форсировать GPU — одно чтение на пачку из 30–60 кадров.

## 2. Как устроен кадр (что уже оптимизировано и как это не сломать)

| Механизм | Где | Правило |
|---|---|---|
| **Фиксированный шаг симуляции 60 Гц** | `loop()` в `src/game.js` | Все таймеры и скорости в `update()` заданы «на кадр при 60 FPS». Не умножайте их на реальное `dt` — скорость игры и так не зависит от монитора. Кадр без нового шага симуляции не рендерится (на 144 Гц рендер идёт 60 раз в секунду). |
| **Кэш поз врагов** | `src/three_enemies.js` | 3 типа × 16 направлений × 6 кадров ходьбы рендерятся один раз и дальше рисуются из кэша. |
| **Кэш пропсов** | `src/three_props.js` | Здания, машины, ящики, лут — один рендер на направление. |
| **Фоновый прогрев кэша** | `schedulePrewarm()` + `runIdleTasks()` | После загрузки моделей все позы рендерятся в простое браузера, иначе первый показ типа даёт фриз 25–55 мс (компиляция шейдеров). **Новый тип врага или пропса — добавьте его в `schedulePrewarm()`.** |
| **Живой рендер** | `src/three_character.js`, `src/three_boss.js` | Василий и босс единственные на экране, поэтому рендерятся каждый кадр. Василий в покое (стоит и целится в одну точку) перерисовывается каждый 3-й кадр. |
| **HUD без лишних записей в DOM** | `setHudText()` / `setHudStyle()` | Не пишите `innerText`/`style` напрямую в `updateHUD()`: каждая запись в кадре — пересчёт стилей и раскладки. |
| **Ленивые запасные спрайты** | `VasiliyAnimator.ensureAssets()` | 2D-спрайты Василия (3.8 МБ) грузятся, только если 3D-модель не загрузилась. |
| **Отсечение по экрану** | `render()`, `EnvironmentRenderer.isVisible()` | Всё, что рисуется в мире, проверяется на попадание в видимую область. |

## 3. Бюджеты на модели

На экране персонажи занимают 80–160 px, пропсы рендерятся в кэш 256 px. Детали сверх бюджета не видны, а грузятся и считаются.

| Тип | Пример | Треугольники | Текстуры | Размер GLB |
|---|---|---|---|---|
| Обычный враг (кэш поз, ~86 px) | `toad_grunt.glb` | ≤ 6–8 тыс. | ≤ 512, WebP | ~0.4 МБ |
| Босс (живой рендер, ~140 px) | `boss_golden_butcher.glb` | ≤ 15 тыс. | ≤ 1024, JPEG/WebP | ≤ 1.5 МБ |
| Василий (живой рендер) | `vasiliy.glb` | тело ≤ 9 тыс., оружие ≤ 1.8 тыс. | ≤ 512, WebP | ~2 МБ |
| Машины, ящики, баки (кэш 256 px) | `car_uaz.glb` | ≤ 5 тыс. | ≤ 512, WebP | ≤ 0.35 МБ |
| Здания | `building_brezhnevka.glb` | ≤ 8 тыс. | ≤ 512–1024, WebP | ≤ 0.5 МБ |
| Лут | `loot_stew.glb` | ≤ 3–4 тыс. | ≤ 512, WebP | ≤ 0.35 МБ |

Генераторы (Rodin, Tripo, Hunyuan) отдают 300+ тыс. треугольников и текстуры 2–4K — **сырые модели в игру не кладём никогда**.

## 4. Пайплайн: картинка → 3D → игра

### 4.1. Генерация 3D по картинке

- **Hyper3D Rodin через Blender MCP** — основной путь (`generate_3d` в MCP). Пробный ключ аддона (`vibecoding`) общий и с дневным лимитом: при `API_INSUFFICIENT_FUNDS` ждём сброса или ставим свой ключ.
  - ⚠️ В рабочей сети крупные загрузки обрываются (SSL EOF): **картинку перед отправкой ужимаем до WebP ≤ 14 КБ** (как `prepare_14k_webp()` в `tools/process_*_pipeline.py`).
- **Hunyuan3D 2.1** — бесплатно, по картинке: https://huggingface.co/spaces/tencent/Hunyuan3D-2.1 → «Gen Textured Shape» → Export: `glb`, *Simplify Mesh* выключить → Transform → Download. Без входа в аккаунт Hugging Face квота GPU маленькая.
- **Tripo** — бесплатный тариф ограничивает число скачиваний, модели публичные (CC BY 4.0 — при публикации нужно указать автора).

Исходники складываем в `blender_assets/<что-то>_concepts/` (папка в `.gitignore`).

### 4.2. Обработка в Blender

На примере босса (рабочий файл `blender_assets/boss_golden_butcher.blend`):

1. Импорт, отделение оружия от тела (по отдельным кускам сетки вдоль оси клинка).
2. Центрирование по стопам, ноги на `Z = 0`, персонаж смотрит в **−Y** (как все модели игры), масштаб.
3. Упрощение сетки (Decimate → Collapse) до бюджета.
4. Скелет, автоматические веса; оружие — дочерний объект кости кисти (`parent_type = 'BONE'`), чтобы клинок не гнулся.
5. Анимации — отдельные actions. Для ударов хронометраж клипа = игровые тайминги (замах / удар / возврат при 60 FPS), см. `attackClips` в `src/three_boss.js`.
6. Экспорт GLB. Важные параметры:
   - `use_active_scene=True` — иначе экспортёр захватит выделенные объекты **из всех сцен** файла;
   - `export_animation_mode='ACTIONS'` — каждый action отдельным клипом;
   - `export_def_bones=False`, если не-деформирующая корневая кость нужна для анимации (вращение в «вихре» босса).

### 4.3. Оптимизация перед игрой

После **каждого** экспорта модели из мастер-`.blend` прогоняйте оптимизатор — иначе в игру вернутся тяжёлые сетки и текстуры:

```bash
blender -b --factory-startup --python tools/optimize_models_blender.py
```

Только нужные модели или пробный прогон в отдельную папку:

```bash
blender -b --factory-startup --python tools/optimize_models_blender.py -- --only toad_grunt,vasiliy --out-dir D:/tmp/opt
```

Новая модель — добавьте её в `TARGETS` в начале скрипта. Скрипт сохраняет имена объектов (код ищет `Vasiliy_Arm_R_Bat`, `Vasiliy_Shotgun` и т.п.), скелет, веса и все анимации. Запускается в фоновом Blender и не трогает открытую сессию.

### 4.4. Проверка и публикация

- Сравните «до/после» в игровом рендере (те же камера, свет и настройки материалов, что в `three_*.js`): при игровом масштабе разницы быть не должно.
- Поднимите версию в URL модели (`?v=…` в загрузчике `three_*.js`) и версии скриптов в `index.html`, иначе у игроков останется старый кэш.

## 5. Blender MCP на новом компьютере

1. Blender 4.2 и аддон **MCP for Blender** (`addon.py` из https://github.com/ahujasid/blender-mcp; у нас стоит версия 1.8) — установить и включить в *Preferences → Add-ons*.
2. Установить `uv`: `pip install uv`.
3. В папке проекта зарегистрировать сервер для Claude Code (анонимная статистика выключена):
   ```bash
   claude mcp add blender -e DISABLE_TELEMETRY=true -- uvx blender-mcp
   ```
4. В Blender: **N → вкладка BlenderMCP →** включить *Hyper3D Rodin* → **Connect to MCP server** (порт 9876).
5. Открыть новую сессию Claude Code в папке проекта — инструменты Blender появятся в ней.

## 7. Идеи на будущее (не сделано)

- **Плавность на 144 Гц.** Логика идёт 60 шагов/с, и без интерполяции кадры на 144 Гц ложатся неравномерно. Можно интерполировать камеру и игрока между шагами — но тогда придётся рендерить каждый кадр монитора (плюс нагрузка на GPU).
- **Вершины Василия не сварены**: 34.6 тыс. вершин на 20.5 тыс. треугольников (швы UV и жёсткие нормали). Сглаживание нормалей уменьшило бы файл примерно вдвое, но может изменить вид — проверять визуально.
- **HiDPI-экраны**: канвас рисуется в CSS-пикселях (`devicePixelRatio` не учитывается) — это про чёткость, не про скорость.
